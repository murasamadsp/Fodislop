TL-CHANGE: scope and decision

Owner: Lighting, dynamic transport, GatherDynamicSource in DynamicPolar.hlsl. Consumer: SolveDynamicLighting near-source receivers. Current per-cell DDA repeats geometry traversal for every angular sample. The experiment proves a complete receiver/emitter bounding box once using the existing clean-cell summed-area table, then integrates the same continuous emitter in a uniform medium.

The box includes the existing cell-plus-texel corner guard. Clean air requires zero occupancy and emission throughout; clean stone requires full occupancy, zero emission and an entirely in-field box. Outside-field air is allowed only by the air proof. Partial occupancy, silhouettes, static emitters and mixed boxes use the existing exact DDA. The source retains continuous bounds, RGB extinction and unbounded scene-linear HDR radiance. No sphere-tracing epsilon or approximate distance field is introduced.

No public/domain API change. Applicable requirements: TL-OWN, TL-API, TL-LIFE, TL-REV, TL-STAGE, TL-VERIFY, TL-CHANGE. JFA and additional distance-field resources are deferred: the existing exact proof can test the uniform-region hypothesis without a new rebuild stage.

Opt-in multi-light dispatch prototype

The «Батчить несколько фонарей» toggle in the same settings window groups polar rays by equal angle-group count and receiver work by equal 8×8 dispatch dimensions. A 32-byte structured descriptor per source carries its receiver rectangle, polar size, uploaded-light index and persistent cache slot. The shader derives each invocation's context from the descriptor and calls the same transport routines as serial dispatch. It does not pad receiver rectangles or merge different polar/cache layers. The descriptor buffer is owned by DynamicLightingSolver and released with the solver; serial dispatch remains the default.

This reduces dispatch submissions only. It does not reduce DDA visits, receiver texels or polar rays; descriptor upload and GPU scheduling may offset the CPU submission savings. The fixed production benchmark uses 16 moving lights, captures the actual world output, and requires fewer dispatches, at least 100 real GPU samples, no more than 2% receiver-stage/GPU-frame/frame-p95 regression in each of three repetitions. No result is claimed until that PlayMode benchmark runs.
